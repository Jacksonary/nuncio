# Nuncio 项目核查报告

核查日期：2026-11-13。范围：当前工作区的 React/TypeScript 前端、Tauri 外壳、6 个 Rust 领域 crate、SQLite/文件存储、测试、依赖及 CI/发布配置。

## 结论

项目的基础架构和测试基础已经建立，但建议先修复数据保护、发件箱状态机、草稿关闭和恢复流程，再继续增加功能或扩大分发。现有测试全部通过，补充的边界验证仍复现了 6 个真实缺陷，说明目前测试对异常路径和状态组合的覆盖不足。

此次仅新增报告和验证材料，未修复或修改业务源码。以下“已复现”来自本地模拟服务器/临时数据库；“代码确认”来自明确的控制流与持久化逻辑；风险条件和实机验证限制均单独说明。

## 一、优先修复的问题

### F01 · P1 · 手动清除缓存破坏 POP3 邮件正文【已复现】

- 位置：[app.rs](../src-tauri/src/commands/app.rs#L62)，[engine/mod.rs](../src-tauri/crates/mail/src/engine/mod.rs#L286)。
- `app_clear_cache` 无条件清空全部 message 的 `body_path`，并删除整个 MIME、附件目录。POP3 的 UIDL 已被记为下载过，下次同步不会重新 RETR；正文读取也没有 POP3 重取实现。
- 验证：下载 POP3 邮件 → 执行清缓存中的相同数据库/文件步骤 → 再次 POP3 同步 → 读取正文，仍返回 `has no cached body`。
- 影响：正常用户操作即可造成正文和未另存附件不可读；服务器副本已删除时无法恢复。
- 建议：区分永久本地原件与可重新下载的缓存；手动清理和 LRU 共用可清理判定。自动 `trim_cache` 已排除 POP3，手动路径应统一遵守这一规则，并与正文下载协调并发。

### F02 · P1 · 备份恢复先删除原数据，整体缺乏回滚【代码确认】

- 位置：[app.rs](../src-tauri/src/commands/app.rs#L183)，[backup.rs](../src-tauri/src/backup.rs#L65)。
- 解密后仅校验格式名和版本，随后逐个删除当前非 local 账户及其凭据，再逐条写入账户、身份、签名和规则。每次 `Db::write` 各自提交，整个恢复不具备原子性。
- 影响：中途遇到数据库约束错误、磁盘写失败或凭据恢复失败，旧数据已被删除，新数据仅恢复一部分；恢复期间也没有全局暂停 PIM 写队列。
- 备份本身只包含账户、设置、身份、签名、规则和可选登录凭据，不包含邮件原文、草稿、发件箱、离线操作、本地日历、联系人和任务。UI 已说明主要导出项，因此不能当作完整数据灾备。尤其恢复同一配置备份会删除非 local 账户下面尚未同步的本地数据，备份无法救回。
- 建议：恢复前做完整语义校验和自动快照；暂停全部相关 worker；在临时数据库完成校验和导入，成功后再切换，并为钥匙串变化设计补偿。明确区分“配置导入”和“完整数据备份”。
- 验收：注入中途 DB/文件/凭据失败后，原账户、待发送邮件、草稿、离线修改仍可用。

### F03 · P1 · 未保存草稿直接发送不会保存 Sent 副本【已复现】

- 位置：[smtp/outbox.rs](../src-tauri/crates/mail/src/smtp/outbox.rs#L131)。
- `post_send` 遇到 `draft_id=None` 直接返回，未执行后面的 `append_to_sent`。新建草稿在首次 3 秒自动保存完成前可能没有 ID；无 ID 发件也属于后端接受的正常输入。
- 验证：模拟 IMAP 具有 Sent 文件夹，SMTP 成功收到邮件，但 `pending_op` 中没有 Sent APPEND。
- 影响：不自动保存已发送邮件的服务商上，邮件确实送出，Sent 中却没有留存。
- 建议：Sent 副本独立于草稿清理执行；传输成功、已发送归档、草稿清理各自保存状态并允许重试。
- 同处附带风险：发送状态先标为 Sent，再执行可能失败的 `post_send`；后处理失败没有独立恢复任务，亦可能永久遗漏归档。

### F04 · P1 · 发件箱恢复会错误重置其他账户正在发送的邮件【已复现状态错误】

- 位置：[smtp/outbox.rs](../src-tauri/crates/mail/src/smtp/outbox.rs#L388)。
- 每次账户的 `process_due` 都执行全局 `recover_stuck`；判断依据是邮件的 `created_at` 超过 10 分钟，而非本次开始发送时间，也不判断是否存在活跃 worker。
- 验证：账户 A 的一小时前入队邮件处于 Sending，运行账户 B 的发件箱轮询后，A 的邮件变为 Pending。
- 影响：多账户、离线积压后重试或手动重试与后台轮询并发时，活跃任务可再次被领取，产生重复发送风险。本次直接证实错误状态重置，未在真实 SMTP 上触发重复投递。
- 建议：增加 `sending_started_at`、发送租约/owner；恢复仅作用于确实失活的任务，通常在启动恢复阶段完成。领取、重试、取消使用带状态条件的数据库转换。

### F05 · P1 · 草稿保存失败仍关闭窗口；关闭到托盘未等待草稿落盘【代码确认，需原生窗口回归】

- 位置：[ComposeView.tsx](../src/modules/mail/compose/ComposeView.tsx#L416)、[关闭编辑器](../src/modules/mail/compose/ComposeView.tsx#L753)、[关闭独立窗口](../src/modules/mail/compose/ComposeView.tsx#L900)，[windows.rs](../src-tauri/src/windows.rs#L425)。
- `saveNow` 保存失败返回 null，已有保存进行中也直接返回 null；两个关闭流程均忽略返回值并继续关闭。
- 主窗口关闭到托盘直接销毁 WebView。当前只为独立 compose 窗口注册关闭前保存；React 的 unmount 尽力保存不能保证在原生销毁 WebView 时完成。自动保存又有 3 秒延迟。
- 影响：附件源文件缺失、磁盘/DB 写失败、正在自动保存或最后几秒仍在输入时，关闭可丢失修改。
- 建议：提供返回同一个 in-flight Promise 的 `flushDraft()`；只在最新版内容成功持久化后允许关闭。主窗口与托盘销毁也使用关闭握手；失败保留编辑器并显示错误。

## 二、功能和一致性问题

### F06 · P2 · 正在发送的邮件允许被删除【已复现】

- 位置：[service/outbox.rs](../src-tauri/crates/mail/src/service/outbox.rs#L455)，由普通 `message_act(Delete)` 调用。
- `outbox_cancel` 会拒绝 Sending，但 `outbox_discard` 无条件删除数据库行和暂存文件。
- 验证：构造 Sending 发件箱记录，discard 成功返回。
- 影响：SMTP 已开始传输时，用户看到邮件已删除，但投递仍可能完成；发送后状态记录和 Sent 归档也可能失败。
- 建议：数据库条件删除仅允许 Pending/Failed，并检查受影响行数；Sending 明确返回冲突并保持可追踪状态。

### F07 · P2 · 有限次数的重复任务不会按次数终止【已复现】

- 位置：[tasks/map.rs](../src-tauri/crates/pim/src/tasks/map.rs#L115)，[tasks/service.rs](../src-tauri/crates/pim/src/tasks/service.rs#L641)。
- 创建下一期时完整复制原 `recurrence.count`，且把起点移到新的到期日，没有扣减次数或保存系列原始锚点。
- 验证：本地每日任务 `COUNT=2`，完成第一期和第二期后，数据库仍存在第三期未完成任务。
- 建议：保留系列 ID、起点和已完成次数，或在符合产品语义的情况下维护剩余次数；验证 COUNT=1/2、跳过逾期、UNTIL、撤销完成和服务商自行生成下一期的情况。

### F08 · P2 · 订阅日历只为第一条主事件保留 RDATE【已复现】

- 位置：[webcal.rs](../src-tauri/crates/pim/src/webcal.rs#L145)。
- `master_seen` 是整个订阅级别的布尔值，导致第二个独立 UID 的主事件也被视为非 master，不保存其 RDATE 精简原文。
- 验证：含两个不同 UID、各有 RDATE 的订阅，第二条的 `raw_ics=None`，额外发生日期丢失。
- 建议：按 UID 组织 master 与 exception；每个没有 RECURRENCE-ID 的主事件都应保存自己的 RDATE，例外事件稳定关联到其主事件。

### F09 · P2 · PIM 队列忽略持久化错误，回滚后不刷新领域缓存【代码确认】

- 位置：[op_worker.rs](../src-tauri/crates/pim/src/op_worker.rs#L100)，[service.rs](../src-tauri/crates/pim/src/service.rs#L2818)，[eventBridge.ts](../src/lib/eventBridge.ts)。
- `mark_in_progress` 和 `mark_done` 的数据库结果被丢弃；数据库写失败时仍可能发起远程副作用，或在远程写成功后仍保留 Pending 状态。
- rollback 后仅发 `op://failed`。前端对该事件只显示 toast，联系人/任务 rollback 本身也没有统一发 changed，界面可能继续显示已回滚的数据直到下一次刷新。
- 建议：领取/提交失败必须显式处理；远程新建配置幂等键或远程 ID 恢复策略；回滚与领域 changed 通知绑定。增加故障注入测试、同一实体连续离线修改测试。

### F10 · P2 · 清除密钥可能仅清除文件副本，钥匙串旧值仍可恢复【代码确认】

- 位置：[secrets.rs](../src-tauri/crates/auth/src/secrets.rs#L147)、[delete](../src-tauri/crates/auth/src/secrets.rs#L207)。
- 任意钥匙串读写错误可使整个进程停用 keyring；之后 delete 跳过钥匙串。即使 keyring 仍启用，delete 失败也仅写 debug 日志并返回文件清理结果。
- 影响：UI 可以报告 client secret 已清除，但旧值仍在系统钥匙串，下次重启读取时重新出现；删除账户也可能留下凭据。
- 建议：删除尝试独立于读取回退开关；真实删除失败应回报，或维护持久 tombstone 并在恢复连接后清理。通过可注入的钥匙串后端测试故障恢复。

### F11 · P2 · 重复任务的“今天”使用 UTC，前端使用本地日期【代码确认】

- 位置：[tasks/map.rs](../src-tauri/crates/pim/src/tasks/map.rs#L10)，[todo/hooks.ts](../src/modules/todo/hooks.ts#L8)。
- `task_set_completed` 的下一期计算使用 UTC 日期，前端“我的一天”和计划日期使用本地日期。
- 影响：例如北京时间 00:00—08:00 完成逾期任务，后端可能仍按昨天推进，生成已逾期任务；负时区也可能跳过本地当天。
- 建议：按系统本地日期或明确的账户/任务时区计算；为 UTC+8、负时区和夏令时切换增加测试。

### F12 · P2 · 部分输入大小上限在完整读取后才检查【代码确认】

- 位置：[webcal.rs](../src-tauri/crates/pim/src/webcal.rs#L63)、[备份导入](../src-tauri/src/commands/app.rs#L188)、[vCard 导入](../src-tauri/crates/pim/src/contacts/service.rs#L859)。
- 订阅的 32 MB 检查在 `response.bytes()` 完成后执行，不能限制下载过程的内存；备份/vCard 也直接整文件读取。
- 影响：异常大订阅、压缩响应或导入文件可能使桌面进程出现较大内存峰值甚至退出。
- 建议：对解压后的流逐块累计并限制字节数；本地先检查 metadata，同时用有上限的读取防止竞态；CPU 密集的解析与备份 Argon2 移到 blocking worker。

### F13 · P2 · 高级设置提前提示保存成功【代码确认】

- 位置：[AdvancedPage.tsx](../src/modules/settings/sections/AdvancedPage.tsx#L43)，[useSettings.ts](../src/lib/useSettings.ts)。
- 保存/清除调用 fire-and-forget `update` 后立即清空输入并弹成功提示。后端失败会回滚 Query 缓存，但这页没有相应失败提示，用户输入的 secret 已被清空。
- 建议：使用 `updateAsync`，仅成功后清空并提示；失败保留草稿，按钮显示保存中并禁止重复提交。

## 三、依赖与发布

### S01 · 开发和测试工具链需要升级

当前 Vite 5.4.21、Vitest 2.1.9 及其传递依赖命中公告，包括 Vitest UI 服务相关代码执行、mocker 路径读取/注入、Vite 开发服务器读取边界与 Windows 编辑器启动问题，以及 tinypool 公告。

这些是开发/测试环境的告警；当前 `vitest run` 命令没有启用 UI 服务，不能将审计 critical 数量解释为已打包桌面应用可以被远程执行代码。生产 npm 依赖审计为 0。

建议同步升级 Vite、React 插件、Vitest 到受维护且修复对应公告的兼容组合，核对 Node 最低版本，并验证 Tauri 开发服务器、HMR 和全部测试。不要直接使用 `npm audit fix --force`。CI 加入官方 registry 的审计或明确处理默认镜像缺少接口的问题。

### S02 · Rust/Linux 依赖存在上游告警

- `glib 0.18.5` 匹配 [RUSTSEC-2024-0429](https://rustsec.org/advisories/RUSTSEC-2024-0429.html)：`VariantStrIter` 迭代器实现不健全，相关调用在优化构建中可能空指针崩溃；公告修复版本为 0.20.0。
- 已通过 Linux 目标依赖树确认它由 Tauri → GTK/WebKit 等原生依赖引入。本项目是否执行受影响迭代器尚未证实，不能据此认定可利用。
- `pin-utils`、`proc-macro-error`、`zvariant`、`zbus_names`、`zvariant_derive` 命中的是停止维护提示，不能按 5 个已证实安全漏洞计数。
- 建议：追踪 Tauri/GTK 上游修复或兼容补丁，做 Linux release 运行验证；将 RustSec 检查纳入 CI，对仍无法消除的上游问题记录适用范围和复核日期。

### S03 · 发布流程尚无质量门禁，Gitee 更新索引可能引用缺失资产【代码确认】

- [release.yml](../.github/workflows/release.yml) 直接构建并公开 release，没有依赖测试 job；CI 仅覆盖 main/master push 与 PR，tag 触发发布不等于对应提交通过检查。
- `releaseDraft:false` 且固定 `prerelease:false`，多平台矩阵尚未全部完成就可能出现部分公开资产；预发布版本也会按正式版处理。
- Gitee 先重写 latest.json 全部 URL，再跳过大于 30 MB 的附件；上传失败仅 warning。因此当更新包过大或上传失败时，索引仍可发布并指向不存在的下载地址。重复发布又会跳过同名附件，可能保留旧 latest.json。
- 建议：测试通过 → 构建所有平台 → 验证资产/签名/索引完整性 → 一次发布；预发布状态从版本推导；镜像索引只引用已验证上传的资产。重建同版本需原子替换对应索引和签名资产。

## 四、性能、维护与测试优化

### O01 · 按窗口/模块拆包，测量冷启动和托盘重开

[app/modules.ts](../src/app/modules.ts) 静态导入全部模块，富文本编辑器也进入主包。构建主 JS 已超过 1.5 MB，且插件同时静态/动态导入导致分包无效警告。

建议先分离 Tiptap 编辑器、设置和日历视图，再按主窗口/阅读窗口/撰写窗口加载需要的代码。记录冷启动、第一次打开写信、关闭到托盘后的 RSS 和重新打开耗时；桌面资源来自本地，gzip 大小并不直接代表用户启动耗时。

### O02 · 增加 staging 清理和准确存储统计

`app_storage_usage` 统计数据库、MIME 和 attachments，未统计 staging/tmp。发件箱 Sent 记录 7 天后 `prune_sent` 仅删除 DB 行；自动保存邮件服务器如 Gmail 不执行 Sent APPEND，也没有相应路径删除原 outbox `.eml`，可长期残留大附件。Bcc 归档新建副本时原 outbox 文件也没有统一回收。

建议按数据库引用做垃圾回收，保护活跃草稿、Pending/Sending 发件箱及 APPEND 队列文件；统计 staging、临时文件和凭据存储占用。缓存淘汰候选也应在 SQL 中直接排除永久原件，避免 500 条候选均为 POP3 时无法淘汰后面的 IMAP 缓存，以及逐条查询账户的额外开销。

### O03 · 把异常路径测试纳入日常质量检查

- 增加本文 6 个已复现问题的正式回归测试；发件箱验证多账户、旧队列、并发重试、取消与投递边界。
- 为草稿编辑器增加 DOM/组件测试：保存失败、保存中继续输入、立即发送、关闭和弹出窗口。现有 Vitest 环境为 node；纯逻辑测试未覆盖这些交互。
- 在隔离数据目录进行 Tauri 冒烟：托盘销毁/重建、通知导航、附件、mailto/webcal、导入和更新。真实 OAuth 与第三方协议兼容需另做账户矩阵验收。
- CI 增加 macOS；加入 rustfmt、Clippy、前端 lint（尤其 React hooks）、依赖审计、`--locked` 和版本一致性检查。Clippy 参数过多可重构为参数对象，确有必要时局部豁免并说明。
